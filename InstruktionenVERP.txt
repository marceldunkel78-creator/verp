# 1) Datenvorlagen manuell nach C:\VERP\Datenvorlagen kopieren:
#    - bestlist.csv
#    - optionale B<YY>_<XXX>.pdf/.docx Dokumente

# 3) Prüfen:
#    cd C:\VERP\backend

# Warum fehlen Bestellungen? (Legacy Procurement, Stand 2026-10-01)
#
# GEMESSEN auf der Entwicklungsdatenbank, 14.604 CSV-Zeilen:
#     Zeilen gelesen                : 14.604
#     Bestellungen in der DB        : 10.142
#     Bisher importiert             :    331
#     Am LIEFERANTEN gescheitert     :  4.008   <-- die eigentliche Ursache
#     Kein Datum/B-Nr. in der CSV   :    117
#
# Es liegt NICHT an den PDF/DOCX-Dateien. Die Dokumente sind optional, eine
# Bestellung wurde auch ohne lesbares Dokument immer angelegt (mit einer
# Dummy-Position). Die Schuld lag am Lieferanten:
#
# Order.supplier ist ein PROTECT-Fremdschluessel und hat keinen Default.
# Ohne Lieferant kann keine Bestellung gespeichert werden, also hat der
# Import sie mit "skipped_supplier" verworfen. In der Spalte "Lieferant"
# der bestlist.csv stehen aber Kuerzel und ausgeschriebene Firmennamen,
# die es so nicht im Lieferantenstamm gibt (DI, Syncron, Printus, Farnell,
# PCO, Yokogawa ...). Der unscharfe Namensabgleich fand sie nicht.
#
# 4.008 von 14.604 Zeilen betraf das - rund 27 Prozent.
#
# ---------------------------------------------------------------------------
# LOESUNG 1: Dummy-Lieferant (automatisch, seit 2026-10-01)
# ---------------------------------------------------------------------------
# Faellt der Lieferantenabgleich aus, legt der Import die Bestellung trotzdem
# an - auf einem Dummy-Lieferanten "Unbekannt (Legacy-Import)". Die Position
# wird dann aus der Warenbezeichnung und Summe der CSV gebaut.
#
# Am Bestelltext steht ein sichtbarer Hinweis, woran man die Faelle erkennt:
#     "Hinweis: Lieferant aus CSV konnte nicht zugeordnet werden. Der
#      Lieferant in der VERP-Bestellung ist ein Dummy-Eintrag."
#
# Im Admin findet man sie ueber:
#     Lieferanten -> "Unbekannt (Legacy-Import)"
# Der Lieferant ist bewusst inaktiv gesetzt, damit er in normalen
# Auswahllisten nicht auftaucht.
#
# ---------------------------------------------------------------------------
# LOESUNG 2: Zuordnungsdatei legacy_supplier_mapping.json (empfohlen)
# ---------------------------------------------------------------------------
# Damit die Dummy-Bestellungen spaeter korrigiert werden koennen, gibt es
# eine editierbare JSON-Datei. Sie liegt DIREKT neben bestlist.csv:
#
#     C:\VERP\Datenvorlagen\legacy_supplier_mapping.json
#
# Diese Datei ist bewusst NICHT im Git (Datenvorlagen/ steht in .gitignore).
# Sie wird auf dem Server wie bestlist.csv manuell nachgeliefert.
#
# Zusaetzlich liegt eine eingecheckte VORLAGE im Backend:
#
#     C:\VERP\backend\legacy_supplier_mapping.json
#
# Sie wird nur gelesen, wenn neben bestlist.csv KEINE eigene Datei liegt.
# Damit ist der Server nicht kaputt, falls die Datei vergessen wurde, und die
# Vorlage kann ohne Zugriff auf Datenvorlagen mitgepflegt werden.
#
# Nach dem Kopieren von Datenvorlagen also diese beiden Dateien pruefen:
#     Test-Path C:\VERP\Datenvorlagen\legacy_supplier_mapping.json
#     Test-Path C:\VERP\backend\legacy_supplier_mapping.json
#
# Aufbau:
#
#   {
#     "_hinweis": "Erlaeuterung, wird ignoriert",
#     "ignore": ["nicht verwendet"],
#     "supplier_map": {
#       "PCO":     {"supplier": "100", "note": "Excelitas-PCO"},
#       "DI":      "Excelitas-PCO",
#       "Syncron": {"supplier": "153", "note": "hier eintragen"},
#       "Printus": {"supplier": "",     "note": "273 Zeilen - offen"}
#     }
#   }
#
# Schluessel = Name aus der Spalte "Lieferant" der bestlist.csv.
# Wert = entweder der FIRMENNAME aus dem VERP oder die LIEFERANTENNUMMER
#        (dreistellig, z. B. "100").
#
# WICHTIGE REGELN:
#   - Leerer Wert "" heisst "noch nicht geklaert" und wird NICHT geraten.
#     Trage hier nie "" ein und erwarte eine Automatik. Ohne Eintrag greift
#     der Dummy-Lieferant.
#   - "ignore" ganz oben: Namen, die keine Bestellung sind. Diese Zeilen
#     werden komplett uebersprungen, es entsteht keine Bestellung.
#   - Komma-Zeilen in der CSV sind einfach nur weitere Zeilen, kein Problem.
#
# Die Datei wird bei JEDEM Lauf neu gelesen. Aenderungen wirken also sofort,
# ein Neustart des Backends ist nicht noetig.
#
# Liste neu erzeugen (z. B. nachdem neue Lieferanten angelegt wurden):
#     cd C:\VERP\backend
#     .\venv\Scripts\Activate
#     python tools\build_legacy_supplier_mapping.py
#
# Achtung: das UEBERSCHREIBT die Datei. Vorher eine Kopie anlegen, wenn
# du Eintraege schon gepflegt hast.
#
# ---------------------------------------------------------------------------
# WORKFLOW IN DER PRAXIS
# ---------------------------------------------------------------------------
# 1) Bestandsaufnahme
#     Admin -> Firmeneinstellungen -> Legacy Procurement Import -> Vorschau
#     Dort siehst du je Zeile: Lieferant, Match-Typ, Aktion.
#
# 2) Zuordnen
#     legacy_supplier_mapping.json im Editor oeffnen und die grossen Brocken
#     eintragen (Firmenname oder Lieferantennummer). Das bringt die meisten
#     Zeilen auf einen echten Lieferanten.
#
# 3) Importieren
#     "Importieren" klicken. Ein zweiter Lauf ist unschaedlich: bereits
#     vorhandene Bestellungen werden uebersprungen und nur noch mit
#     Dokumenten verknuepft.
#
# 4) Dummy-Bestellungen korrigieren
#     Admin -> Lieferanten -> "Unbekannt (Legacy-Import)" -> Bestellungen
#     anzeigen. In der Bestellung steht der Originalname der CSV noch in
#     den Notizen ("Legacy Lieferant: Syncron"). Nach dem Eintrag im JSON
#     den Lieferanten je Bestellung korrigieren.
#
# ---------------------------------------------------------------------------
# DOKUMENTE
# ---------------------------------------------------------------------------
# Die B<YY>_<XXX>.pdf/.docx muessen im SELBEN Ordner wie bestlist.csv liegen.
# Der Import ordnet sie ueber den Dateinamen zu:
#     B07_042.pdf  ->  B-Nr. 042 aus dem Jahr 2007
# Aus dem Dokument werden die Positionen gelesen. Das funktioniert bei
# .docx (Tabellen) besser als bei .pdf (Layout). Wird nichts gefunden,
# entsteht trotzdem eine Position aus der CSV - die Bestellung fehlt nie.
#
# Sind die Dokumente NICHT da, fehlen sie auch im VERP. Das ist der
# wahrscheinlichste Grund fuer fehlende Bestelldokumente: die Dateien
# liegen dann nicht neben der CSV. Pruefen:
#     Get-ChildItem C:\VERP\Datenvorlagen -Filter "B*_*.pdf"
#
# Aktueller Stand im Entwicklungs-Datenvorlagen: 0 Dateien nach dem Muster.
# Auf dem Server die B<YY>_<XXX>.*-Dateien also noch nachliefern.

# ============================================================
# LAGER-SYNC AUS EXCEL (Warenlager automatisch abgleichen)
# ============================================================

# Zweck:
# Die Lagerartikel werden weiterhin in Excel-Listen (nach Warengruppe oder
# Hersteller benannt) gepflegt. Diese Listen werden automatisch abgeglichen
# und NEUE Artikel direkt im VERP angelegt. Es muss nichts mehr umformatiert,
# nach CSV konvertiert und manuell importiert werden - und bestehende
# VERP-Daten werden NIE veraendert.
#
# Ablauf je Lauf:
# 1. Alle passenden Dateien (Standard *.xls*) im eingestellten Verzeichnis
#    werden gelesen. .xls, .xlsx, .xlsm und .csv sind unterstuetzt.
# 2. Die Kopfzeile wird automatisch erkannt (Titelfunken, Leerzeilen egal).
#    Spalten werden ueber Alias-Namen zugeordnet (S/N = Seriennummer = serial).
#    Die Spaltenreihenfolge ist egal.
# 3. Jede Zeile wird abgeglichen:
#      - mit Seriennummer  -> Match auf Seriennummer (Trennzeichen egal)
#      - ohne Seriennummer -> Match auf Produktname + Lieferant + Best-Nr.
# 4. Nur was NOCH NICHT existiert, wird neu angelegt.
# 5. Alles Bekannte bleibt unveraendert.
#
# ---------------------------------------------------------------------------

# 1) Quelle einstellen (in C:\VERP\backend\.env)
#
#    INVENTORY_EXCEL_DIR=\\\\fileserver\\Lager\\Warenlager
#    INVENTORY_EXCEL_PATTERN=*.xls*
#
#    WICHTIG: Die Lagerlisten liegen aktuell fast ausschliesslich im ALTEN
#    .xls-Format. "*.xlsx" wuerde fast nichts finden! "*.xls*" erfasst
#    .xls, .xlsx und .xlsm in einem Durchgang.
#
#    Pfad pruefen:
#    cd C:\VERP\backend
#    .\venv\Scripts\Activate
#    python manage.py shell -c "from inventory.management.commands.sync_inventory_from_excel import get_setting; import os; p=get_setting('INVENTORY_EXCEL_DIR'); print(repr(p)); print('OK' if p and os.path.isdir(p) else 'FALSCH')"
#
#    WICHTIG: Nicht os.environ.get verwenden! In diesem Projekt liest Django
#    die .env ueber python-decouple, das schreibt aber NICHTS in
#    os.environ. Ein Test mit os.environ.get liefert daher IMMER None,
#    auch wenn die .env korrekt ist. Immer get_setting() nutzen.
#
#    Zaehlung, was gefunden wird:
#    python manage.py shell -c "from inventory.management.commands.sync_inventory_from_excel import get_setting; from pathlib import Path; import glob; p=get_setting('INVENTORY_EXCEL_DIR'); f=glob.glob(str(Path(p)/'*.xls*')) if p else []; print(len(f),'Dateien in',p)"

# 2) Spalten-Mapping anpassen, falls sich Header aendern
#
#    Standarddatei: backend\inventory\excel_mapping.json
#    Je logischem Feld eine Liste moeglicher Header. Wird eine Spalte nicht
#    erkannt, meldet der Lauf sie als "unbekannte Spalten".
#
#    Arbeitsblaetter ausschliessen (keine Lagerartikel):
#    In excel_mapping.json unter "skip_sheets" eintragen, z.B.
#        "skip_sheets": ["Getestete Optiken", "Preisliste", "Kondensor-Sets"]
#    Oder dateibezogen: "Dateiname.xls::Blattname"
#    Oder die Umkehrung - nur bestimmte Blaetter importieren:
#        "only_sheets": ["Blatt1", "Blatt2"]

# 3) ZUERST immer als Probelauf (aendert NICHTS)
#
#    cd C:\VERP\backend
#    .\venv\Scripts\Activate
#    python manage.py sync_inventory_from_excel --dry-run
#    python manage.py sync_inventory_from_excel --path "\\fileserver\Lager\Warenlager" --dry-run
#
#    Nur geaenderte/aktuelle Dateien:
#    python manage.py sync_inventory_from_excel --since 2026-09-01 --dry-run
#
#    Schnelltest - nur die ersten N DATEIEN (empfohlen, sonst dauert es lange):
#    python manage.py sync_inventory_from_excel --max-files 5 --dry-run
#    ACHTUNG: ein begrenzter LIVE-Lauf importiert auch nur diesen Teil!
#    Der Rest wird beim naechsten vollstaendigen Lauf nachgeholt.
#
#    Nur die ersten 20 Datenzeilen GESAMT (ueber alle Dateien):
#    python manage.py sync_inventory_from_excel --limit 20 --dry-run

# 4) Echter Abgleich
#
#    python manage.py sync_inventory_from_excel
#
#    Wiederholen ist unschaedlich: bereits importierte Artikel werden
#    uebersprungen. Ein zweiter Lauf legt also nichts doppelt an.

# 5) Ergebnisse auswerten
#
#    Konsolenausgabe:
#      Zeilen gelesen / Neu angelegt / Bereits vorhanden / Dublette (echt) /
#      Mehrdeutig / Uebersprungen (Excel offen) / Blaetter ohne Lagerartikel /
#      Wiederholte Kopfzeilen / Fehler
#
#    Reportdatei: C:\VERP\logs\inventory_sync_JJJJMMTT_HHMMSS.csv
#      Spalten: source_file, source_sheet, source_row, action,
#               inventory_number, serial_number, name, message
#
#    action-Bedeutung:
#      create     = neu angelegt
#      skip       = bereits vorhanden, unveraendert
#      duplicate  = exakte Dublette in der Quelldatei (nichts angelegt)
#      ambiguous  = mehrere Lagerartikel passen zum Schluessel, ohne S/N nicht
#                   entscheidbar -> NICHTS angelegt, bitte manuell zuordnen
#      locked     = Datei war in Excel geoeffnet -> uebersprungen, kommt beim
#                   naechsten Lauf automatisch nach
#      no_header  = Blatt ohne Lagerartikel (Info-/Preistabelle)
#      error      = Datei nicht lesbar
#
#    Auswertung "ambiguous" (wichtig, meist die gr�sste Gruppe):
#      Eine Excel-Zeile ohne S/N beschreibt einen Mengenartikel, waehrend im
#      VERP mehrere Einzelstuecke dazu existieren. Beispiel:
#        "xyz-Tisch" ohne S/N, im VERP I-00030, I-00032, I-00033 ...
#      Diese Zeilen werden bewusst NICHT importiert, weil sonst grundlos
#      Artikel entstuenden. Sie brauchen eine manuelle Entscheidung.
#
#    Im Admin: Warenlager -> nach "Quelldatei" filtern.

# 6) Automatisch laufen lassen
#
#    cd C:\VERP\scripts
#    Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope Process
#    .\sync-inventory.ps1
#    .\sync-inventory.ps1 -DryRun
#    .\sync-inventory.ps1 -ExcelPath Z:\Warenlager
#
#    Als geplante Aufgabe registrieren (einonceig, als Administrator):
#    .\register-inventory-sync-task.ps1 -ExcelPath Z:\Warenlager -DailyAt "02:00"
#
#    Status:
#    Get-ScheduledTaskInfo -TaskName "VERP-Inventory-Sync" |
#        Select-Object LastRunTime, LastTaskResult

# 13) Netzwerkpfad (UNC) - die drei häufigsten Fehler
#
# 1) FALSCHE DIAGNOSE MIT os.environ
#    Der Befehl
#        python manage.py shell -c "import os; print(os.environ.get('INVENTORY_EXCEL_DIR'))"
#    liefert IMMER None, auch wenn die .env korrekt ist.
#    Grund: Django liest die .env ueber python-decouple (verp/settings.py).
#    decouple schreibt die Werte aber nicht in os.environ.
#    RICHTIG:
#        python manage.py shell -c "from inventory.management.commands.sync_inventory_from_excel import get_setting; import os; p=get_setting('INVENTORY_EXCEL_DIR'); print(repr(p)); print('OK' if p and os.path.isdir(p) else 'FALSCH')"
#
# 2) BACKSLASHES IN DER .env
#    decouple interpretiert KEINE Escape-Sequenzen. Deshalb gilt:
#        FALSCH:  INVENTORY_EXCEL_DIR=\\\\server\\Text\\Company\\Lager
#        FALSCH:  INVENTORY_EXCEL_DIR=\\server\\Text\\Company\\Lager   (nur 1 vorn)
#        RICHTIG: INVENTORY_EXCEL_DIR=\\server\\Text\\Company\\Lager    (2 vorn, 1 hinten)
#        RICHTIG: INVENTORY_EXCEL_DIR=//server/Text/Company/Lager     (Forward slashes)
#    Die ersten beiden sind in der .env IDENTISCH - man kann also gar nicht
#    an der Schreibweise unterscheiden. Nutze Forward slashes, dann ist es
#    eindeutig. Der Import normalisiert falsch escapte Pfade inzwischen
#    selbst und warnt, falls der Ordner nicht erreichbar ist.
#
# 3) KEIN LAUFWERKSBUCHSTABE NÖTIG
#    Der Explorer-Fehler "Dieser Unterordner kann nicht zugeordnet werden"
#    ist normal und unproblematisch. Ein Netzlaufwerk laesst sich nur auf
#    einen FREIGABE-ROOT mappen, nicht auf einen Unterordner.
#    Du brauchst es aber gar nicht: der Import funktioniert direkt mit
#    \\server\Text\Company\Lager. Es ist keine Freigabe noetig.
#    Pruefen (muss JA ergeben):
#        Test-Path "\\server\Text\Company\Lager"
#    Laeuft der Task als SYSTEM, dann SYSTEM sieht die Freigabe nur ueber
#    das Computerkonto. Zwei Loesungen:
#        a) Laufwerk mappen (benoetigt Freigabe-Root):
#               net use Z: \\server\Text /persistent:yes
#               INVENTORY_EXCEL_DIR=Z:\Company\Lager
#        b) Aufgabe mit einem echten Benutzerkonto registrieren, der auf die
#           Freigabe zugreifen darf.
#
# ---------------------------------------------------------------------------
#
# Empfohlene Einstellung fuer die aktuelle Ordnerstruktur:
#
#     INVENTORY_EXCEL_DIR=//server/Text/Company/Lager
#     INVENTORY_EXCEL_PATTERN=*.xls*
#     INVENTORY_EXCEL_EXCLUDE_DIRS=alte Lagerlisten,Backup
#
# Referenzmessung auf diesem Pfad (Entwicklungsserver, 2026-09-30):
#     alle Ordner rekursiv              : 141 Dateien
#     mit INVENTORY_EXCEL_EXCLUDE_DIRS   :  97 Dateien (-44 Archive)

#     Get-ChildItem <pfad> -File -Include *.xls   liefert 0 Treffer!
#     -Include greift nur, wenn der Pfad selbst ein Wildcard enthaelt.

#         Get-ChildItem <pfad> -Recurse -Include *.xls
#     Der Import selbst ist davon nicht betroffen (Django glob/rglob).#

# LAGER-SYNC: VERHALTEN AB 2026-10-06 (WICHTIG)

# Ursache der leeren Warenlager-Eintraege: der naechtliche Sync hat Zeilen
# OHNE Seriennummer, OHNE Kunde und OHNE Bestellnummer als eigene Artikel

# Treffer) und wurden bei JEDEM Lauf erneut angelegt - so entstanden tausende
# Artikel mit Lieferant "Unbekannt" (Nr. 226) und ohne Inhalt.
#
# Ab 2026-10-06 gilt:
#
# 1) LEERE ZEILEN WERDEN NICHT MEHR IMPORTIERT
#    Kriterium: keine Seriennummer UND kein Kunde UND keine Bestellnummer
#    (weder Best.-Nr. noch Auftrag). Solche Zeilen erscheinen im Report als
#    action=skip_empty und erzeugen KEINEN Lagerartikel.
#
# 2) KEINE NEUEN LIEFERANTEN MEHR
#    Ist der Lieferant aus der Liste im Stamm nicht auffindbar (exakt,
#    normalisiert, enthalten, unscharf), wird KEIN neuer Lieferant angelegt.
#    Der Artikel faellt auf den Platzhalter "Unbekannt" (226) zurueck; der
#    urspruengliche Name steht als Warnung in der Ausgabe und im Report.
#    Die Lieferanten-Stammdaten werden nur noch manuell gepflegt.
#
# 3) AUERAEUMEN DER ALTEN MUELL-ARTIKEL
#    Neues Management-Command (Standard: Dry-Run, aendert nichts):
#        cd backend
#        .\venv\Scripts\Activate
#        python manage.py cleanup_empty_inventory_items
#    Listet alle Artikel OHNE Seriennummer, OHNE Kunde und OHNE Bestellnummer
#    auf - gruppiert nach Quelldatei und Eingelagert-Monat. IMMER zuerst
#    den Dry-Run und den Report pruefen: ein Artikel ohne S/N kann ein
#    legitimer Mengenartikel sein! Eingrenzen z.B. mit:
#        python manage.py cleanup_empty_inventory_items --supplier-number 226
#        python manage.py cleanup_empty_inventory_items --stored-since 2026-10-01

# ============================================================
# LANGSAMES LIEFERANTEN-VERZEICHNIS (Ursache + Behebung)
# ============================================================
#
# Stand 2026-10-02. Zwei voneinander unabhaengige Ursachen.
#
# 1) Falscher Host im Frontend  (~2100 ms pro API-Aufruf)
#
#    .env.development zeigte auf  http://localhost:8000
#
#    "localhost" loest Windows zu ::1 (IPv6) auf. Django lauscht aber nur
#    auf 127.0.0.1 (IPv4). Das ::1-Paket wird dann ueber das Tailscale-
#    Interface geschickt (dessen MTU ist 1280 statt 1500) und laeuft in
#    einen Timeout von ca. 2 Sekunden.
#
#    Gemessen am 02.10.2026, gleicher Server, gleiche Anfrage:
#        http://localhost:8000   ~2100 ms
#        http://127.0.0.1:8000   ~90 ms      -> Faktor 23
#
#    Beweis, dass es nicht die Datenbank war: auch /api/notifications/
#    recent/ (2 Byte Antwort) brauchte 2085 ms, und zwar unabhaengig von
#    Cookies, Endpunkt und Trefferzahl. Ein reines Datenbankproblem
#    kann nicht skalieren.
#
#    Behebung: REACT_APP_API_URL auf http://127.0.0.1:8000/api
#    Zusaetzlich '[::1]' in die ALLOWED_HOSTS aufgenommen.
#
#    WICHTIG: Nach dieser Aenderung MUSS das Frontend neu gestartet
#    werden (nur ein Browser-Reload reicht nicht).
#
# 2) Kreuzprodukt beim Zaehlen der Verknuepfungen  (~5900 ms)
#
#    Die Verknuepfungszahlen auf der Lieferantenkachel wurden mit
#    Count(rel, distinct=True) in EINEM gemeinsamen LEFT JOIN annotiert.
#    Bei einem Lieferanten mit 995 Lagerartikeln x 3109 Bestellungen sind
#    das rund 3,1 Mio. Join-Zeilen, die COUNT(DISTINCT) zurueckzaehlen
#    muss.
#
#    Behebung: fuenf einzelne Subqueries mit Coalesce(..., 0).
#    Geprueft ueber alle 123 Lieferanten: 0 Abweichungen.
#
#    MERKREGEL: In Listen-Annotationen NIE mehrere Count() in einen
#    gemeinsamen JOIN. Immer Subquery je Verknuepfung.
#
# Pruefen:
#     cd C:\Users\mdunk\Documents\VERP\backend
#     $env:VERP_TEST_PASSWORD = 'mein-testpasswort'   # nur fuer DIESE Skripte
#     $env:VERP_BASE        = 'http://127.0.0.1:8000'
#     C:\Users\mdunk\Documents\VERP\.venv\Scripts\python.exe tools\check_running_server.py
#     ... tools\measure_running_server.py
#     ... tools\compare_localhost_vs_ipv4.py
#     ... tools\verify_supplier_subquery.py
#     Remove-Item Env:\VERP_TEST_PASSWORD              # danach wegraeumen
#
# Wichtig: Diese Skripte setzen das Passwort des Testnutzers KURZZEITIG
# und stellen es danach wieder her. Sie fragen deshalb bewusst nach
# VERP_TEST_PASSWORD und haben keinen festen Wert im Code - sonst
# wuerde das Passwort in die Git-Historie wandern und auf dem Server
# mit dem echten postgres-Konto kollidieren.
#
# Achtung bei eigenen Testskripten mit Login:
#   - force_login() wirkt bei JWT-Cookie-Auth NICHT; echter Login ueber
#     /api/auth/login/ noetig.
#   - Testclient braucht HTTP_HOST=localhost, sonst blockt ALLOWED_HOSTS.

#     sonst "No module named 'verp'".

# ============================================================
# ANMELDUNG 401 / REFRESH 400 ("Anmeldedaten fehlen.")
# ============================================================
#
# Stand 2026-10-06. Symptom in den Browser-DevTools (Network):
#   POST /api/auth/login/          -> klingt erfolgreich
#   GET  /api/users/me/ u.a.       -> 401 "Anmeldedaten fehlen."
#   POST /api/auth/refresh/        -> 400 "Dieses Feld ist erforderlich."
# Die Zugangsdaten sind korrekt - das Passwort ist NICHT das Problem.
# Ursache ist, dass die JWT-Cookies (access_token/refresh_token) im Browser
# nicht ankommen bzw. nicht mitgesendet werden. Beide Meldungen sind nur
# Folgen desselben Mangels:
#   401 "Anmeldedaten fehlen."          = access_token-Cookie fehlt am Request
#   400 "Dieses Feld ist erforderlich." = refresh_token-Cookie fehlt komplett
#
# Es gibt ZWEI unabhaengige Ursachen. Beide kamen mit dem Update 2026-10-02
# (Commit 312e687) in die Produktion:
#
# 1) PRODUKTION (http://verp.intern.local): Secure-Cookies auf plain HTTP
#
#    Bei DJANGO_DEBUG=False markiert Django die JWT-Cookies als "secure".
#    Auf http:// wirft der Browser solche Cookies sofort wieder weg - der
#    Login sieht erfolgreich aus, danach ist alles 401.
#
#    FIX (backend/verp/jwt_cookie_views.py, seit 2026-10-06): das "secure"-
#    Flag wird jetzt aus request.is_secure() abgeleitet - es wird nur bei
#    echtem HTTPS gesetzt. Damit heilt das Problem ohne Konfiguration.
#    In der .env des Produktionsservers zusaetzlich setzen:
#        SECURE_SSL_REDIRECT=False
#        SESSION_COOKIE_SECURE=False
#        CSRF_COOKIE_SECURE=False
#    Danach Backend neu starten: Restart-Service VERP-Backend
#
# 2) ENTWICKLUNG (localhost:3000 -> 127.0.0.1:8000): Cross-Site-Cookies
#
#    Bis 312e687 zeigte REACT_APP_API_URL auf http://localhost:8000/api -
#    same-site zu localhost:3000, die Cookies liefen mit. Die Performance-
#    Umstellung auf http://127.0.0.1:8000/api (wegen des ::1-Timeouts, siehe
#    "LANGSAMES LIEFERANTEN-VERZEICHNIS") hat die API aber CROSS-SITE
#    gemacht (localhost != 127.0.0.1):
#      - SameSite=Lax-Cookies werden bei XHR nicht mitgesendet
#      - moderne Browser lehnen Cookies aus Drittkontexten komplett ab
#    Symptom identisch zu 1) - weder Admin- noch User-Account kamen rein.
#
#    FIX (seit 2026-10-06): REACT_APP_API_URL=/api in .env.development und
#    "proxy": "http://127.0.0.1:8000" in package.json. Die Aufrufe bleiben
#    same-origin ueber den Dev-Server, der Proxy-Zaehler ist weiterhin der
#    schnelle IPv4-Host (der ::1-Timeout bleibt ebenfalls behoben).
#    WICHTIG: npm start NEU starten - nur ein Browser-Reload reicht nicht,
#    weil die Env-Werte beim Start in das Bundle eingebacken werden.
#
# SCHNELLTEST NACH DEM FIX (Entwicklung):
#   1) Backend:  cd backend; .\venv\Scripts\Activate; python manage.py runserver
#   2) Frontend: cd frontend; npm start
#   3) Browser DevTools -> Network oeffnen, anmelden.
#      Der POST muss an http://localhost:3000/api/auth/login/ gehen (NICHT
#      an 127.0.0.1:8000). In der Response steht Set-Cookie: access_token=...;
#      HttpOnly. Danach muss GET /api/users/me/ mit 200 antworten.
